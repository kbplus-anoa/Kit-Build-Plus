# score — 设计
用户体验/页面设计

## 页面与交互
> 总是遵循本·施奈德曼（Ben Shneiderman）的界面设计八条黄金法则，且须全部达成。
> 与用户讨论方案阶段须说明为何达到了这八条

**评分报告页**是学生提交后看到的唯一"结果页"，也是双模式共用的同一个组件
（只有"能否返回修改"不同）。逐条对照：

1. **保持一致性**：四类错误在报告里永远用同一套名称、同一套符号、同一顺序
   （缺失 → 多余 → 游离 → 反转），与论文术语对应但不出现英文缩写。
2. **允许熟练用户走捷径**：报告顶部先给一句话结论（"你连对了 4 条，
   漏了 2 条"），细节折叠在下方；不需要看全表也能明白结果。
3. **提供有信息量的反馈**：分数写成 `4 / 6` **而不是只写 0.67** —— 分子分母
   同时可见，学生才知道"差多少条"。四类错误各给条数，不合并成一个"错误数"。
4. **把对话设计成结束**：学习模式结尾是"还能改，回去补充缺失的 2 条"按钮；
   测验模式结尾是"本次成绩已记录"，并明确不再有下一步。
5. **防止错误**：报告本身不改数据；**学习模式下点击返回修改前**弹一句
   "你的分数会随着修改变化，学习模式分数不作为成绩"。
6. **允许轻松撤销**：学习模式可反复返回修改直至一致；测验模式明确不可返回，
   且在提交前就告知（见 `rebuild` 的确认框），不在报告页才说。
7. **保持内部对话记忆**：报告顶部标注"目标图 v1 · 第 2 次提交 · 学习模式"，
   让"这份报告是哪一次"永远可查。
8. **减少短期记忆负担**：差异可视化**直接在图上标**（缺失的连接画虚线、
   多余的高亮、方向反了画反向箭头），而不是让学生对着列表在脑内重建图。

## 数据流

```
TargetMap（分母）+ Submission（分子）
   │
   ├─ lookup：目标键集合 vs 提交键集合（O(E) 查表，不做图匹配）
   │
   └─ classify（顺序固定：reversed → leaving → excessive → lacking）
          │  每类先排除更具体者 ⇒ 一条错写只归一类
          v
     ScoreResult { total, correct, errors[] }
          ├─ ratio  → 分数（0~1，无部分分）
          └─ summary → 四类计数（供界面与 CSV）
```

契约出口：`kbp/contracts/report.py` 的 `ScoreResult` / `ErrorChain`。
**错误链只带原始三元组**，不带"正确答案参考"与置信度（已定方案 1）。

## 无障碍功能
> 含且只含：
> 1. 色盲
> 2. 计算机使用不熟练者

- **色盲**：四类错误不用红/黄/蓝区分，用**形状 + 文字标签**：缺失画**虚线**、
  多余画**加粗实线**、游离画**波浪线**、反转画**反向箭头**；每种都附中文标签。
- **计算机使用不熟练者**：分数用 `4 / 6` 全写并在旁解释"共 6 条标准命题，
  你连对 4 条"；不用"FMS""正规化增益"等术语；图例常驻在图旁而非悬停才出现。
